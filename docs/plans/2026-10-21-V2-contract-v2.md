# V2: memory contract v2 (spec 2026-10-21 §2, §4)

The v1 `concierge.memory` body carries the valid facts and one summary. V2 adds, without removing anything, what the
page needs to show by kind what is remembered about the visitor, what this session's memory work did, and what the
agent carries about itself (spec §1.4). Every new key is optional: a v1 page reads a v2 body and a v2 page reads a v1
body. Decisions this plan had to take are D17 *default* in `docs/decisions.md`.

## The §2 body, word for word

From `docs/specs/2026-10-21-integrated-concierge.md` §2 (the page's spec carries the same text):

- **`concierge.memory` v2 body** (sent at session start, after every merge, after a compaction, and once more as
  the final message before the agent leaves): the v1 keys `visitor`, `facts`, `summary`, `updated_at`, plus
  - `"v": 2`
  - `"about_visitor"`: `{ "profile": [fact…] (the valid typed-slot facts, same shape as v1 facts), "episodes": [ {"visit": int, "started_at": iso, "ended_at": iso|null, "summary": str|null} ] (newest first, at most 5; the current visit has ended_at null and summary null until the session ends), "events": [ {"ts": iso, "type": "fact_added"|"fact_invalidated"|"fact_deleted"|"gate_rejected"|"extraction_ran"|"remember"|"forget", "detail": str} ] (this session only, newest first, at most 12; detail is one short plain sentence with no instruction text and no URL) }`
  - `"about_agent"`: `{ "knowledge": {"words": int, "est_tokens": int, "sources_commit": str, "sections": [str]}, "instructions_est_tokens": int, "memory_block_chars": int|null, "working": {"items": int, "est_tokens": int, "compacted": bool, "compactions": int}, "cache": {"cached_share": float|null} }`
  - `"retention_days": 30`
- **`concierge.get_memory`** returns the v2 body.

**One build path.** V2-05 puts the agent view and the payload callable in a new module (`concierge/memory_view.py`;
`session.py` is 219 lines and only gains wiring): `AgentView(agent, compactor, collector).about_agent() -> AboutAgent`
reads `chat_ctx` on the event loop (it is not thread-safe), then the store part runs on the writer's thread:
`writer.call(build_memory_payload, store, thread_id, about_agent=view, events=ring.items())`. The publisher and
`concierge.get_memory` use the **same** callable (`serve_rpcs` takes it instead of calling `current_memory` with its
own arguments), so the RPC returns what the topic last sent, minus `updated_at`. None of it runs in a
`conversation_item_added` handler: the publisher's `schedule` only starts a task.

## Publish points

| When | Who calls `publisher.schedule()` | Since |
|---|---|---|
| session start, after the greeting is queued | `start_session` | C6 |
| after every merge | the writer's `on_merged` (session's callback) | C6 |
| after an applied compaction | `Compactor(on_compacted=publisher.schedule)`, called right after `self.applied += 1` (`compactor.py:148`) | **V2-05** |
| the final one before the agent leaves | `session_end._work`, after the summary step and `end_visit` and `session_ended`, then `publisher.idle()` | V1-02 |
| on request | `concierge.get_memory` builds the same body (it is a reply, not a send) | C6 |

`do_remember` / `do_forget` merges are not `on_merged` merges (the tools call `merge` / `apply_fact_ops` themselves);
today the page sees them at the next merge or the final send. V2-04 has both tools call an `on_changed` callback
(the session passes `publisher.schedule`) after they note their events, so a tool's line shows at once (D17 (h)).

## The size rule

`MAX_BODY_BYTES = 15 * 1024` (UTF-8). `events` (12) and `episodes` (5) are capped by count when the body is built,
before any size check. Worst case measured with the real shapes (`$HARNESS_SCRATCH/size.py`, ASCII values): 4 single
slots at 120 characters and 2 × 8 set items at 60 make 20 facts, 4,532 bytes; `profile` repeats them (another
4,532); 5 episodes with 400-character summaries 2,531; 12 events at 120 characters 2,305; `about_agent` with 20
80-character section titles 1,958; total **16,671 > 15,360**. With 2- to 4-byte UTF-8 characters the episodes alone
can pass 10 KB. So the cap stays a trimmer, not a count:

1. the oldest facts first, each dropped from `facts` **and** `profile` together (`profile == facts` always),
2. then the oldest events (the end of the newest-first list),
3. then the oldest episodes (the end of the list),
4. never a v1 key, `v`, `about_agent` or `retention_days`.

It keeps v1's one-pass arithmetic (each dropped item costs its JSON plus a comma; a fact costs twice). V2-05's
`test_the_largest_allowed_body_fits` builds the body of the V2-05 step (5 episodes at 400 characters, 12 events at
120, every set slot 8 × 60, every single slot 120, a 1,500-character memory block count, 20 section titles, the
maximal fact list) and asserts `body_bytes <= 15 * 1024` and that the v1 keys are intact;
`test_a_multibyte_body_trims_events_then_episodes` does the same with 4-byte characters and asserts the drop order.

## The schema

`tests/contract/memory.schema.json` (draft 2020-12) gains `v` (`const: 2`), `about_visitor`, `about_agent`,
`retention_days` (`type: integer`) under `properties`, each nested object with `additionalProperties: false` and all
of its own keys required (inside a v2 object nothing is optional; a page renders a missing **top-level** key as "not
reported"). `required` stays `["visitor", "facts", "summary", "updated_at"]`, so a v1 body validates. `events` and
`episodes` carry `maxItems` 12 and 5, `type` an `enum` of the seven names, nullable fields `["string", "null"]` /
`["integer", "null"]` / `["number", "null"]`. A test keeps the enum equal to `EventType`'s args, as
`test_memory_payload_slot_enum_matches_models_slots` does for slots.

## The `visit_summaries` migration

`concierge/schema.py`: `SCHEMA_VERSION = 3`; `"visit_summaries"` joins `TABLES`; `SCHEMA` gains

```sql
CREATE TABLE IF NOT EXISTS visit_summaries (       -- V2: one row per visit, the episodes of concierge.memory v2
  thread_id  TEXT NOT NULL REFERENCES threads(id) ON DELETE CASCADE,
  visit      INTEGER NOT NULL,                     -- threads.attributes.visits when the session started
  started_at INTEGER NOT NULL,                     -- ms
  ended_at   INTEGER,                              -- ms; NULL until the session's summary step
  summary    TEXT,                                 -- NULL until then, and when the summary failed or was skipped
  UNIQUE (thread_id, visit)
);
```

and `MIGRATIONS[3]` is the same `CREATE TABLE IF NOT EXISTS …` statement: one statement, the shape C6-03 used for
`MIGRATIONS[2]` (the `ALTER TABLE … ADD COLUMN created_at`), run by `StoreBase._create_schema` for each version
between the file's `user_version` and `SCHEMA_VERSION` (`store_base.py:118-121`). The `UNIQUE` constraint is the
index, so no second statement is needed. A version-2 file opened by `Store()` gains the table and reads version 3; a
new file gets the DDL directly. Rolling back to V1 code refuses a v3 file (`_create_schema` raises on a newer
version): V2-03 adds that line to MORNING.md's deploy notes.

## Store and session

- `Store.begin_visit(thread_id, visit, started_at) -> None`: one fenced write (`self.write(thread_id, None, …)`),
  `INSERT … ON CONFLICT (thread_id, visit) DO NOTHING`, so it is idempotent and raises `ThreadMissing` after an erase.
- `Store.end_visit(thread_id, visit, ended_at, summary: str | None) -> None`: one fenced write, an `UPDATE` only. An
  erased thread raises `ThreadMissing` from the fence and nothing is re-created; a missing row (its `begin_visit`
  failed) updates nothing (D17 (b)).
- `Store.visit_episodes(thread_id, limit=5) -> list[VisitEpisode]` (`VisitEpisode` in `models.py`, ms integers),
  newest first by `visit`.
- `session.py`: the `session_started` background task calls `begin_visit(preloaded.thread_id, preloaded.visits,
  started_ms)` on the writer's thread before it journals `session_started`, and that task is created **before** the
  start `publisher.schedule()`, so its write is queued on the writer's one-thread executor ahead of the start read
  and the start body already lists the current visit with `ended_at` and `summary` null. `started_ms` is the store
  clock's `now_ms()` when `start_session` began.
- `session_end.py` (250 lines, at the cap): `write_summary` returns the text it stored, or None (failed, skipped,
  stale, erased); `_work` then calls `end_visit(thread_id, preloaded.visits, now, text)`, unless erased, before
  `session_ended` and the final send. To make room, V2-03 moves `write_summary` and `forgotten_values` into a new
  `concierge/summary_step.py`. `VisitorState.last_visit_summary` (what the prompt renders, v1's `summary`) is unchanged.
- **Erasure**: `"visit_summaries"` joins `_CHILD_TABLES` in `concierge/store_erasure.py`, so `forget_me` and
  `purge_idle` delete the rows explicitly (the FK cascade is the backstop). A forget_me landing during the shutdown:
  `end_visit` raises `ThreadMissing`, caught like the summary's.

## Events (V2-04)

`MergeResult` gives ids only, and `on_merged` is sync on the event loop (no store read there), so V2-04 adds
`MergeResult.changes: list[FactChange]` (`FactChange {kind: "added" | "invalidated", slot, value}`, in
`merge_result.py`), filled by `merge` from the applied `AddFact` ops and the decision's live entries for the
invalidated targets. Values travel in memory only; the journal still never holds them (D8). The session's `on_merged`
calls `ring.note_merge(result)`, which notes, oldest first so the list reads newest first: `extraction_ran` (only
when the run changed or rejected something, D17 (d)), then one `gate_rejected` per gate rejection with a reason in
words, then `fact_invalidated`, then `fact_added`. `do_remember` notes `fact_invalidated` for what it replaced and one
`remember`; `do_forget` notes one `fact_deleted` per slot it deleted from and one `forget`. The tools get the ring
through `ConciergeAgent(events=…)` (`memory_writer.py` is at 250 lines and does not change). A forget_me clears the
ring (`add_erase_hook(writer, ring.clear)`). Line wording is D17 (a). Every detail goes through `check_text`
(`concierge/gate.py`) and is at most 120 characters, else the type's value-free form is used.

## Build order between the features

`events=`. V2-03 adds the episodes (and extends V2-02's seeded-store test), V2-04 the ring, V2-05 the agent view and
the trimmer's event and episode steps. Each leaves the suite green on its own.

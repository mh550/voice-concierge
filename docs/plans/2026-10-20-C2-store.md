## Connection and time

- `sqlite3.connect(path, isolation_level=None, timeout=5.0, check_same_thread=False)`. `isolation_level=None`
  turns off Python's implicit `BEGIN`, so the store issues `BEGIN IMMEDIATE` itself. `timeout=5.0` is SQLite's
  busy timeout: a writer waits up to 5 s for another process's write lock.
- Per connection: `PRAGMA journal_mode=WAL` (persists in the file; a no-op when already WAL), `PRAGMA
  foreign_keys=ON`, `PRAGMA synchronous=NORMAL` (safe with WAL), `PRAGMA secure_delete=ON` (deleted content is
  zeroed, which erasure needs), `PRAGMA journal_size_limit=0` (a WAL reset by any later checkpoint is truncated to
  zero bytes, so old frames don't linger when `forget_me`'s own checkpoint was blocked).
- One connection per `Store` per process, guarded by a `threading.Lock`. Store methods are synchronous. Async
  callers (C3 preload, C4 extractor and tools) call them through `asyncio.to_thread`, never on the turn path
  (spec §4.4).
- **Time.** Every `*_at`, `valid_from`, `valid_to` and `ts_ms` column is an INTEGER of **milliseconds since the
  Unix epoch (UTC)**, from `Store(clock=…)` (default `now_ms()` = `time.time_ns() // 1_000_000`). Tests inject a
  clock. Milliseconds order two facts written in the same second; `id` breaks any tie. `idle_ttl_s` stays in
  seconds, as the spec names it. Days for `daily_session_counts` are UTC `YYYY-MM-DD` strings.

## Schema (`concierge/schema.py`), columns as spec §4.2, B7 and B9

Created with `CREATE TABLE IF NOT EXISTS`, so two processes opening one file is safe, and `PRAGMA
user_version = 1` marks the schema version for later migrations.

```sql
CREATE TABLE IF NOT EXISTS threads (
  id             TEXT PRIMARY KEY,                 -- uuid4 hex, never reused (see "Ids")
  visitor_id     TEXT NOT NULL UNIQUE,             -- the scope: one thread per visitor (B2)
  created_at     INTEGER NOT NULL,                 -- ms
  last_active_at INTEGER NOT NULL,                 -- ms; set by get_or_create_thread
  idle_ttl_s     INTEGER NOT NULL DEFAULT 2592000, -- 30 days (B6)
  attributes     TEXT NOT NULL DEFAULT '{"visits": 1}',  -- JSON: {"visits": int}
  version        INTEGER NOT NULL DEFAULT 0        -- the fence (§4.2)
);

CREATE TABLE IF NOT EXISTS state (
  thread_id  TEXT PRIMARY KEY REFERENCES threads(id) ON DELETE CASCADE,
  state      TEXT NOT NULL CHECK (length(CAST(state AS BLOB)) < 8192),  -- VisitorState JSON
  updated_at INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS facts (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,  -- never reused (see "Ids")
  thread_id     TEXT NOT NULL REFERENCES threads(id) ON DELETE CASCADE,
  slot          TEXT NOT NULL,
  value         TEXT NOT NULL,
  confidence    REAL NOT NULL CHECK (confidence BETWEEN 0 AND 1),
  source        TEXT NOT NULL CHECK (source IN ('user_said', 'user_typed', 'user_asked_to_remember')),
  channel       TEXT NOT NULL CHECK (channel IN ('voice', 'text')),
  turn_id       TEXT NOT NULL,
  created_at    INTEGER NOT NULL,
  valid_from    INTEGER NOT NULL,
  valid_to      INTEGER,                            -- NULL while valid
  superseded_by INTEGER REFERENCES facts(id) ON DELETE SET NULL
);
CREATE INDEX IF NOT EXISTS facts_valid ON facts(thread_id, valid_to);

CREATE TABLE IF NOT EXISTS journal (               -- append-only
  id         INTEGER PRIMARY KEY,
  thread_id  TEXT NOT NULL REFERENCES threads(id) ON DELETE CASCADE,
  session_id TEXT NOT NULL,
  ts_ms      INTEGER NOT NULL,
  type       TEXT NOT NULL,                        -- JournalType Literal, checked in models.py
  payload    TEXT NOT NULL DEFAULT '{}'            -- JSON
);
CREATE INDEX IF NOT EXISTS journal_thread ON journal(thread_id, id);

CREATE TABLE IF NOT EXISTS anonymous_turn_metrics (  -- B9: no visitor id, no text, numbers only; survives erasure
  id                     INTEGER PRIMARY KEY,
  session_id             TEXT NOT NULL,            -- random uuid4 hex per session
  turn                   INTEGER NOT NULL,
  eou_ms                 REAL,
  stt_ms                 REAL,
  llm_ttft_ms            REAL,
  tts_ttfb_ms            REAL,
  total_ms               REAL,
  memory_on_turn_path_ms REAL,
  preload_ms             REAL,
  extraction_ms          REAL,
  prompt_tokens          INTEGER,
  cached_tokens          INTEGER,
  compacted              INTEGER NOT NULL DEFAULT 0 CHECK (compacted IN (0, 1))
);

CREATE TABLE IF NOT EXISTS daily_session_counts (  -- B7: survives erasure; kept 2 days
  key   TEXT PRIMARY KEY,                          -- sha256(visitor_id + day) hex
  day   TEXT NOT NULL,                             -- UTC YYYY-MM-DD
  count INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS messages_for_michael (  -- §4.6, written in C8; created now so erasure covers it
  id         INTEGER PRIMARY KEY,
  thread_id  TEXT NOT NULL REFERENCES threads(id) ON DELETE CASCADE,
  text       TEXT NOT NULL,
  contact    TEXT,
  created_at INTEGER NOT NULL
);
```

Notes on the columns:

- `anonymous_turn_metrics` holds exactly the §6 `concierge.metrics` fields plus `id` and `session_id`. It has no
  timestamp, so its rows can't be lined up against a visit by time. The `session_id` is a fresh uuid4 per session,
  also used in that session's journal rows; erasure deletes the journal, which is the only link from a session id
  back to a visitor in this database. It has no foreign key to `threads`.
- `daily_session_counts` and `anonymous_turn_metrics` have no foreign keys, so nothing cascades into them.
- `attributes` holds only `{"visits": n}`. The spec's "display name" is **not** copied there: it is `state.name`,
  derived from the `name` fact, so a `forget` of the name removes it everywhere at once.
- `journal.type` has no SQL `CHECK`. The `JournalType` Literal in `models.py` constrains it (C2-02 step 4), so C5
  can add a type for compaction without a table rebuild (see "Proposed changes").
- The `CHECK` on `state` is a backstop for the 8 KB cap; the pydantic validator is the real check.
- `sqlite_sequence` appears in `sqlite_master` because `facts` uses `AUTOINCREMENT`. Table-name tests filter
  `name NOT LIKE 'sqlite_%'`.

### Ids

- **Thread ids are uuid4 hex, never integers.** An `INTEGER PRIMARY KEY` reuses the largest id after that row is
  deleted. After a "Forget me", the next new visitor could get the erased visitor's thread id, and an extraction
  still in flight for the old session would then write into the new visitor's thread. A random id can't collide.
- **Fact ids use `AUTOINCREMENT`** for the same reason. The extractor and the page refer to facts by id; a stale
  `DELETE(fact_id=17)` must never hit a newer fact that took id 17. Integers stay short for the extractor's prompt.
- Every fact lookup is `WHERE id = ? AND thread_id = ?`. A fact id from another thread is "not found", never
  touched (spec §4.0, "scope is one visitor per thread").

## Models (`concierge/models.py`, pydantic v2)

```python
SlotName = Literal["name", "role", "company", "follow_up_wanted", "interests", "asked_about"]
Source = Literal["user_said", "user_typed", "user_asked_to_remember"]
Channel = Literal["voice", "text"]
JournalType = Literal["session_started", "session_ended", "user_turn", "agent_turn", "memory_preloaded",
                      "extraction_ran", "fact_added", "fact_invalidated", "fact_deleted", "turn_metrics",
                      "gate_rejected", "error"]           # exactly the §4.2 list

class SlotSpec(BaseModel, frozen=True): kind: Literal["single", "set"]; cap: int; max_items: int = 1
SLOTS: dict[SlotName, SlotSpec]                          # the catalogue below

class Fact(BaseModel): id: int; thread_id: str; slot: SlotName; value: str; confidence: float (0..1);
    source: Source; channel: Channel; turn_id: str; created_at: int; valid_from: int;
    valid_to: int | None = None; superseded_by: int | None = None
    # validator: value stripped, non-empty, no control characters, len(value) <= SLOTS[slot].cap

class VisitorState(BaseModel): name, role, company, follow_up_wanted: str | None = None;
    interests: list[str] = []; asked_about: list[str] = []; last_visit_summary: str | None = None
    # field caps: single 120, set items 60 and at most 8 items, summary 500 characters
    # model_validator(mode="after"): len(self.model_dump_json().encode()) < 8192, else ValueError

class AddFact(BaseModel): op: Literal["add"] = "add"; slot: SlotName; value: str; confidence: float = 1.0;
    source: Source; channel: Channel; turn_id: str; supersedes: list[int] = []
class InvalidateFact(BaseModel): op: Literal["invalidate"] = "invalidate"; fact_id: int; superseded_by: int | None = None
class DeleteFact(BaseModel): op: Literal["delete"] = "delete"; fact_id: int
FactOp = Annotated[AddFact | InvalidateFact | DeleteFact, Field(discriminator="op")]
class ApplyResult(BaseModel): version: int; added: list[int]; skipped: list[int]

class Thread(BaseModel): id: str; visitor_id: str; created_at: int; last_active_at: int; idle_ttl_s: int;
    visits: int; version: int

class TurnMetrics(BaseModel, extra="forbid"): turn: int; eou_ms, stt_ms, llm_ttft_ms, tts_ttfb_ms, total_ms,
    memory_on_turn_path_ms, preload_ms, extraction_ms: float | None = None;
    prompt_tokens, cached_tokens: int | None = None; compacted: bool = False
```

`TurnMetrics` has exactly the §6 `concierge.metrics` fields; C6 reuses it for the topic body. `extra="forbid"` is
what keeps text out of `anonymous_turn_metrics`.

**Why the 8 KB validator can fire although every field is capped.** The caps count characters; JSON counts bytes.
A maximal ASCII state is about 2 KB, and one written entirely in 4-byte UTF-8 is about 7.9 KB. Escaping is what
breaks the cap: a control character dumps as `\u0001`, six bytes. `Fact` rejects control characters, so a state
derived from facts never trips the validator; it guards `VisitorState`s built elsewhere (C5's summary).

### The slot catalogue (§4.0, "Profile, not collection")

| Slot | Kind | Value cap | Items | On ADD | On DELETE |
|---|---|---|---|---|---|
| `name` | single | 120 chars | 1 valid | supersedes the current valid value (old gets `valid_to`, `superseded_by` = new id); an equal value is a no-op | extractor: invalidates; `forget`: deletes |
| `role` | single | 120 chars | 1 valid | same | same |
| `company` | single | 120 chars | 1 valid | same | same |
| `follow_up_wanted` | single | 120 chars | 1 valid | same; the value says what follow-up the visitor wants (e.g. "a call about the RAG project") | same |
| `interests` | set | 60 chars per item | at most 8 | appends with dedupe (equal after `casefold()` and whitespace collapse is a no-op); a 9th valid item invalidates the **oldest** (`superseded_by` = new id) | removes one item: extractor invalidates it; `forget` deletes it |
| `asked_about` | set | 60 chars per item | at most 8 | same | same |

`last_visit_summary` is not a slot. It is not a fact either: it lives only in `VisitorState`, is written by C5's
session-end summary (at most 3 sentences, 500 characters), and `recompute_state` carries it over unchanged.

**Where the catalogue's ADD rules run.** The store applies ops literally: an `AddFact` inserts a row and
invalidates the ids in its `supersedes` list. Turning "ADD name=Ann" into "insert Ann, supersede fact 12" is the
C4 merge's job (`concierge/merge.py`, from `SLOTS`), and it runs inside the fenced write through the callable form
of `apply_fact_ops` (below), so it decides against the facts at the version it writes. Keeping the store literal
is also what C2-03's concurrent-writers step requires: its 40 facts all stay valid, which no slot rule would allow.
`recompute_state` still enforces the shape on read (single slots take the newest valid fact, sets the newest 8),
so a state is well-formed whatever the facts table holds.

## Store API (`concierge/store.py`)

| Method | Does | Bumps `version` |
|---|---|---|
| `Store(path, clock=now_ms)` | opens the connection, sets the pragmas, creates the schema | — |
| `get_or_create_thread(visitor_id) -> Thread` | one `BEGIN IMMEDIATE`: `INSERT … ON CONFLICT(visitor_id) DO UPDATE SET last_active_at = excluded.last_active_at, attributes = json_set(attributes, '$.visits', json_extract(attributes, '$.visits') + 1), version = version + 1 RETURNING …`, then `INSERT OR IGNORE` an empty `state` row. A new row has `version = 0`, `idle_ttl_s = 2592000`, `attributes = {"visits": 1}`. The only call that creates a thread (§4.2) | on revisit |
| `thread_for(visitor_id) -> Thread \| None`, `version(thread_id) -> int` | reads; `version` raises `ThreadMissing` | no |
| `write(thread_id, expected_version, fn) -> T` | the fence (below) | yes, by 1 |
| `apply_fact_ops(thread_id, ops, *, based_on=None) -> ApplyResult` | the reload-and-reapply loop (below) | by 1 per call |
| `add_fact(thread_id, AddFact) -> Fact` | `apply_fact_ops(thread_id, [op])`; `valid_from = created_at = now` | yes |
| `invalidate_fact(fact_id, superseded_by=None, *, thread_id=None)` | `apply_fact_ops(tid, [InvalidateFact(...)])`, so it journals and recomputes the state like any op: sets `valid_to = now` (and `superseded_by`); the row stays. `FactMissing` if the op is skipped | yes |
| `delete_fact(fact_id, *, thread_id=None)` | `apply_fact_ops(tid, [DeleteFact(...)])`: really deletes the row (the `forget` tool; B5) and recomputes the state, so a forgotten value leaves `state` too. `FactMissing` if skipped | yes |
| `valid_facts(thread_id) -> list[Fact]` | `valid_to IS NULL`, ordered by `valid_from, id` | no |
| `fact_history(thread_id) -> list[Fact]` | every remaining row, valid or not, same order (for `memory_history.py`) | no |
| `state(thread_id) -> VisitorState` | reads the `state` row | no |
| `recompute_state(thread_id) -> VisitorState` | `derive_state(valid_facts, previous)` and stores it, in one fenced write | yes |
| `journal(thread_id, session_id, type, payload)` | appends a row (`ts_ms = now`); `type` validated against `JournalType` first | yes |
| `journal_rows(thread_id) -> list[JournalRow]` | in insertion order (`ORDER BY id`) | no |
| `add_turn_metrics(session_id, metrics: TurnMetrics)` | one `INSERT` into `anonymous_turn_metrics`; no thread involved | — |
| `count_session(visitor_id, day) -> int` | `INSERT … ON CONFLICT(key) DO UPDATE SET count = count + 1 RETURNING count`, key `sha256((visitor_id + day).encode()).hexdigest()` | — |
| `forget_me(visitor_id) -> bool` | the erasure sequence (below); `False` when the visitor has no thread | — |
| `purge_idle(now) -> int`, `purge_daily_counts(now) -> int` | the TTL purge (below); both return rows removed | — |

Errors (in `store.py`): `StoreError` ← `ThreadMissing`, `VersionConflict(current: int)`, `FactMissing`.

**Every write to a thread's rows is one `BEGIN IMMEDIATE` transaction that bumps `threads.version` once** (spec
§4.2: "every write … checks and bumps a version"). That covers fact ops, state, journal appends and the revisit
touch. The two anonymous tables are not thread rows and are written in their own short transactions. Appends
that don't depend on state (`journal`, `recompute_state`) pass `expected_version=None` to `write`, meaning "the
version read inside the transaction", so they never conflict; they still fail with `ThreadMissing` once the thread
is gone, which is what makes erasure win.

## The fence (`Store.write`)

```python
def write(self, thread_id: str, expected_version: int | None, fn: Callable[[Connection], T]) -> T:
    with self._lock:
        conn.execute("BEGIN IMMEDIATE")             # takes the write lock now, not at the first write
        try:
            row = conn.execute("SELECT version FROM threads WHERE id = ?", (thread_id,)).fetchone()
            if row is None:
                raise ThreadMissing(thread_id)       # erased or never created: never re-create it
            current = row[0]
            if expected_version is not None and current != expected_version:
                raise VersionConflict(current)
            result = fn(conn)                        # the delta: inserts, invalidations, state, journal
            fence = current if expected_version is None else expected_version
            bumped = conn.execute(
                "UPDATE threads SET version = version + 1 WHERE id = ? AND version = ?",
                (thread_id, fence)).rowcount
            if bumped != 1:                          # can't happen under BEGIN IMMEDIATE; kept as the fence
                raise VersionConflict(current)
            conn.execute("COMMIT")
            return result
        except BaseException:
            if conn.in_transaction:                  # SQLite may have rolled back on its own already
                conn.execute("ROLLBACK")             # a failed fn or a conflict leaves no row
            raise
```

`BEGIN IMMEDIATE` takes SQLite's reserved lock at once, so no other process can write between the version read
and the `UPDATE`. A plain `BEGIN` would take it at the first write and could fail mid-transaction with
`SQLITE_BUSY`. Readers are never blocked (WAL).

## Reload and reapply (`Store.apply_fact_ops`)

`ops` is either a list of `FactOp`s or a callable `(valid_facts: list[Fact]) -> list[FactOp]`. The callable is
how C4's merge re-decides slot rules against fresh facts; a list is re-validated.

```python
def apply_fact_ops(self, thread_id, ops, *, based_on: int | None = None) -> ApplyResult:
    expected = based_on if based_on is not None else self.version(thread_id)   # ThreadMissing if gone
    for attempt in range(1, MAX_ATTEMPTS + 1):                                 # MAX_ATTEMPTS = 5
        try:
            now = self._clock()                                # fresh on each attempt
            return self.write(thread_id, expected, lambda conn: fact_ops.apply(conn, thread_id, ops, now))
        except VersionConflict:
            if attempt == MAX_ATTEMPTS:
                raise
            time.sleep(random.uniform(0.01, 0.03) * attempt)   # jittered backoff: let the other writer finish
            expected = self.version(thread_id)                 # reload the version *after* the sleep, re-apply
```

`fact_ops.apply(conn, thread_id, ops, now)` runs inside the transaction:

1. **Reload**: read this thread's valid facts on `conn`.
2. Resolve: `ops(valid_facts)` if callable, else the list.
3. Apply each op in order. `AddFact` inserts (`created_at = valid_from = now`) and then invalidates each id in
   `supersedes` with `superseded_by` = the new id. `InvalidateFact` sets `valid_to = now`. `DeleteFact` deletes.
   A target that isn't a fact **of this thread** (deleted meanwhile, or another thread's id) is skipped and listed
   in `ApplyResult.skipped`; invalidating an already-invalid fact is a skip too (the first `valid_to` stands).
4. Journal `fact_added` / `fact_invalidated` / `fact_deleted` in the same transaction. Payloads carry ids, slot,
   source, channel and turn id, **never the value**, so a `forget` (a real delete) leaves the value nowhere.
5. Recompute and store `VisitorState` (`derive_state`).

So one call is one transaction and one version bump, however many ops it carries. `based_on` is for C4's
extractor: it passes the version it loaded facts at before its LLM call, so a write that happened during the call
is detected and the ops re-resolved. After five conflicts the `VersionConflict` propagates; the background caller
journals `error` and drops the batch (the next extraction sees the same turns again).

**What the fence doesn't give** (README, C2-05): 1.8 has no lease, so two live sessions for one visitor can
interleave turns. The fence only guarantees that neither overwrites the other's writes.

## Erasure (`Store.forget_me`)

```
1. BEGIN IMMEDIATE
2. SELECT id FROM threads WHERE visitor_id = ?          -> none: ROLLBACK, return False
3. DELETE FROM facts                WHERE thread_id = ?
   DELETE FROM state                WHERE thread_id = ?
   DELETE FROM journal              WHERE thread_id = ?
   DELETE FROM messages_for_michael WHERE thread_id = ?
   DELETE FROM threads              WHERE id = ?        (children first; the FK cascades are a second net)
4. COMMIT
5. VACUUM                                               (outside any transaction; rewrites the file)
6. PRAGMA wal_checkpoint(TRUNCATE)                      (moves the vacuumed pages into the db, empties the WAL)
7. return True
```

`anonymous_turn_metrics` and `daily_session_counts` are untouched (B7, B9). Steps 3–4 are a private
`_erase_thread(conn, thread_id)` shared with the TTL purge.

- **Why steps 5 and 6.** With `secure_delete=ON`, `DELETE` zeroes the freed content, but in WAL mode the old pages
  still sit in the `-wal` file until a checkpoint. The prototype found the marker text in `-wal` after `DELETE`
  and after `VACUUM`, and in neither file after `wal_checkpoint(TRUNCATE)`. If another process holds a read
  transaction, the checkpoint returns busy; `forget_me` logs it, and the next checkpoint finishes the job.
- **The rows are gone at step 4.** `forget_me` holds `Store._lock` for the whole sequence. A failure in steps 5–6
  (`database is locked` after the 5 s busy timeout) is caught and logged, and `forget_me` still returns True, so
  the page's RPC answers `{"ok": true}` (§6) for an erasure that did happen. Log lines carry the thread id's first
  8 characters at most, never the `visitor_id` or any value.
- **Erasure wins** (§4.2). Every later write goes through `write`, which raises `ThreadMissing` when the row is
  gone, and nothing but `get_or_create_thread` inserts into `threads`. A write already holding the lock when
  `forget_me` starts commits first, and `forget_me` then deletes what it wrote. Either order ends with zero visitor
  rows. Cancelling the session's pending extraction and compaction tasks, and skipping the shutdown callback's
  final extraction, are C4/C6 work on top of this.
- `forget_me` itself doesn't journal (the journal is being erased).

## TTL purge (`Store.purge_idle`, `Store.purge_daily_counts`)

- `purge_idle(now: int)` (ms): `SELECT id FROM threads WHERE last_active_at + idle_ttl_s * 1000 < ?`, then
  `_erase_thread` for each, all in one `BEGIN IMMEDIATE`, then one `VACUUM` and checkpoint if any went. Returns
  the count. It's the spec's "`last_active_at` + `idle_ttl_s` < now" with the units reconciled.
- `purge_daily_counts(now: int)`: deletes rows **older than 2 days**: `day < (UTC date of now) − 2 days`. Rows
  for today, yesterday and the day before stay; the cap itself only ever reads today's row. `day` strings compare
  correctly as text.
- Both run at worker start and daily (B6). The wiring (an `AgentServer` setup hook or a timer in the worker
  process) is C6's; C2 ships the methods.

## `scripts/memory_history.py`

`python scripts/memory_history.py <db> <visitor_id>` prints one line per fact in `fact_history` order
(`valid_from`, then id), tab-separated: `slot`, `value`, `valid_from` (ISO 8601 UTC), `valid_to` (ISO) or
`current`, `superseded_by` (fact id) or `-`. It checks the file exists (else exit 2) and opens it read-only
(`file:<db>?mode=ro`, through a `Store.open_readonly(path)` that skips schema creation), so it never creates or
writes a database; an unknown visitor
prints `no thread for this visitor` to stderr and exits 1. Deleted facts don't appear: they're gone (B5). It runs
on Michael's box against the live db and prints visitor data to his terminal only.

## Prototypes (scratch, before writing this plan)

- **Erasure in WAL mode.** 200 marker rows inserted, deleted, `VACUUM`ed: the `-wal` file still held all 200
  markers after the `DELETE` and after `VACUUM`; after `PRAGMA wal_checkpoint(TRUNCATE)` (returned `(0, 0, 0)`)
  neither file held any. Hence steps 5–6 of the erasure sequence and `test_forget_me_leaves_no_bytes_on_disk`.
- **The fence under contention.** Two `spawn` processes on a `Barrier`, 20 single-row writes each through
  read-version → `write` → retry (5 attempts, backoff `uniform(0.01, 0.03) × attempt`), 30 runs: every run ended
  with 40 rows and version 40; 29 first-attempt conflicts in total and none on a second attempt (3.3 s for all 30).

## Risks

- **Flaky concurrency test.** The prototype says no, but C2-03 must run `tests/test_concurrent_writers.py` 20 times
  in a loop before passing and report the result.
- **`check_same_thread=False` with `asyncio.to_thread`.** Safe only because every connection use is under
  `Store._lock`; C2-03's review should check no method skips it.
- **Residual links (not fixed; noted for the README's limits).** The `daily_session_counts` key is an unsalted
  hash, so whoever holds a `visitor_id` can confirm a day's sessions; an HMAC with a local key would close that.
  Metric values are stored rounded to whole milliseconds (`add_turn_metrics` rounds), so they're harder to match
  exactly against LiveKit Agent Insights, which does know the participant.
- **VACUUM cost.** It rewrites the whole file, which is fine for a database of a few hundred KB. It runs on
  erasure and purge only, never on a turn.

## C2-02 build notes (Opus review of the C2-02 diff: 0 Critical, 2 Important, 9 Minor)

- **Opening a fresh file from several processes at once.** `PRAGMA journal_mode=WAL` on a file not yet in WAL takes
  an exclusive lock, and SQLite does not run the busy handler for it: the reviewer saw `database is locked` at
  once in 15 of 15 runs with 2 processes. `Store` retries each pragma on "locked" for up to the busy timeout (5 s),
  then checks the mode really is `wal`. Test: `test_processes_opening_a_fresh_file_together_all_succeed`
  (4 spawn processes × 3 fresh files; passed in 10 of 10 runs in a loop).
- **Fact values** reject Unicode categories Cc, Cf, Cs, Co, Cn, Zl and Zp, not only Cc. That covers U+2028/U+2029
  line separators, bidi overrides, zero-width characters and lone surrogates, which `json.loads` can produce and
  UTF-8 can't store.
- `TurnMetrics` rejects NaN and infinity. `add_turn_metrics` takes only a uuid4 hex `session_id` (B9: no visitor
  or room id can be passed in). `journal` payloads must be dicts and fail before the transaction. `user_version` is
  set only when it is lower; a newer file raises `StoreError`. The clock is read under the lock, and
  `last_active_at` never moves backwards. `visits` is `coalesce(..., 0) + 1`.
- `write(fn)`: `fn` must use only `conn`. The lock is a plain `Lock`, so calling a Store method from `fn`
  deadlocks. C2-03's callable form of `apply_fact_ops` passes `valid_facts` in for this reason.
- **Deferred to C2-03.** `VisitorState` isn't frozen, so mutating a list in place gets around its caps.
  `recompute_state` must build the state with `model_validate` before storing it, never mutate and store.
- `store.py` is at 249 lines. C2-03's fact helpers go in `concierge/fact_ops.py`, as the module layout says.

## C2-03 build notes (Opus review of the C2-03 diff: 0 Critical, 2 Important, 7 Minor)

- **Layout.** To keep every module under 250 lines, `store.py` is split. `concierge/store_base.py` (`StoreBase`)
  holds the errors (`FactMissing` is new), `now_ms`, the connection with its pragmas and schema, the lock
  (`_locked`, `_transaction`, `_read`), `_checkpoint` and `add_turn_metrics`. `concierge/store.py` (`Store(StoreBase)`)
  holds threads, `write`, the journal and the fact API, and re-exports the errors. `concierge/fact_ops.py` holds the
  in-transaction helpers and `derive_state`. Line counts: 226, 175 and 158.
- **Builder's calls.** `apply_fact_ops`, `add_fact`, `invalidate_fact` and `delete_fact` take `session_id=""`, which
  becomes the journal rows' session id (C4 passes the live session's id). Fact-op journal payloads hold ids, slot,
  source, channel, turn id and supersedes, never the value. `ApplyResult.version` is the version after the write.
  `invalidate_fact` with a `superseded_by` from another thread, or equal to itself, is a skip, so it raises `FactMissing`.
- **Review fixes (tests first, 5 RED → GREEN, plus 1 test-gap test).**
  - (Important) `delete_fact` checkpoints the WAL (`wal_checkpoint(TRUNCATE)`, best effort, logged when busy), so
    a forgotten value leaves the `-wal` too. C2-04's `forget_me` should reuse `StoreBase._checkpoint`.
  - (Important) A Store method called from inside `write` (and so from an `apply_fact_ops` callable) now raises
    `StoreError` instead of deadlocking: `_locked` records the owning thread.
  - A `based_on` ahead of the thread's version raises `StoreError`.
  - `derive_state` takes "newest" by id (commit order), not by `valid_from`, because the clock can step back.
  - Sets hold each value once (equal after casefold and whitespace collapse; the newest spelling wins).
  - The rollback test now fails after the inserts.
  - Hung concurrency children are terminated.
- **Not fixed; for C4.**
  - `invalidate_fact` and `delete_fact` take `thread_id` optionally, as planned. **C4's `forget` tool must pass its
    visitor's `thread_id`**, so that a fact id supplied by the model can't reach another visitor's fact.
  - An `apply_fact_ops` callable holds SQLite's write lock while it runs, so it must be fast and pure: decide from
    the facts it gets, with no I/O and no LLM call.
  - The concurrency test can't tell the version check apart from `BEGIN IMMEDIATE` simply serializing the writes.
    The single-process tests cover the check itself.
- **Verified.** `test_concurrent_writers.py` passed 20 of 20 runs in a loop (and 10 of 10 in the reviewer's).
  I ran 24 mutants: 22 were caught and 2 are equivalent (a 6th loop attempt that is never reached; the op re-check,
  whose job reading the facts back also does). Mutants must run with `PYTHONPATH=<copy>`: under pytest, the editable
  install otherwise imports the worktree, not the mutated copy.
